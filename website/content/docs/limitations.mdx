Solitary is not a magic safety switch. It protects a machine boundary, not the authority you give an agent.

## The boundary itself can fail

Solitary aims for full isolation: an agent with root in its container should not be able to reach the host. A VM is the strongest boundary a workstation offers, but it is still made of software, and software has bugs. Isolation can be lost through a flaw in any layer the cell runs on:

- **The hypervisor and host kernel** — KVM or Apple's Virtualization framework, and QEMU with its emulated devices. Escapes from a VM are rare, but they are found. `gpu: true` adds virglrenderer and the host's GPU driver to this list.
- **Lima** — it turns the machine definition into a running VM and runs the host-side agents for port forwarding and user-mode networking. A setting Lima honours can widen the boundary; Solitary inspects the definition it creates for that, which is only as complete as the checks it knows to make.
- **The guest kernel, podman and nftables** — they enforce the container and the network policy. A flaw here does not reach the host on its own, but it can defeat an allow list or a VPN-only rule.
- **Solitary itself** — it renders the machine definition, writes the firewall, moves files across the boundary and handles secrets. A mistake in any of those can open a path the design forbids.

Every one of these is treated as a vulnerability, not as expected behaviour. None of them can be ruled out. Keep the host OS, Lima and Solitary up to date, prefer a restrictive network policy over the default, and do not give a cell anything — a credential, a network path, a port — that you could not afford to lose if the boundary failed. If you find a way through it, [report it privately](https://github.com/balakin/solitary/security/advisories/new).

## It does not protect granted authority

An agent can still push to every repository reachable by a token, call every API allowed by the network policy, and modify anything inside its cell. Give it credentials with the smallest scope possible.

## It does not make images trustworthy

A VM prevents an image from directly modifying the host, but the image still runs code with the secrets and network access you granted. Review images and build definitions.

## An attached terminal is shared with the cell

`solitary shell`, `up` and `exec` connect the cell to your terminal as it is. That is what makes nvim, tmux, true colour and the mouse work in a cell, and it means whatever runs there can send your terminal emulator any escape sequence it understands. Solitary cannot filter that stream without breaking the programs it is for, so what the terminal does with it is part of what you trust a cell with:

- **The clipboard.** OSC 52 lets a program write to your clipboard, and in some terminals read it. A cell that can read your clipboard sees whatever you last copied — a password included — which is exactly what [`send --clipboard`](/docs/artifacts#paste-a-screenshot) is designed never to allow. Check that your terminal refuses or asks before a read: kitty (`clipboard_control`) and Ghostty (`clipboard-read`) ask by default, and WezTerm ignores read requests. Writes are allowed by all three, so a cell can leave a command on your clipboard; look at what you paste from a session with an agent in it.
- **The terminal itself.** Escape sequences are parsed by your terminal emulator, and emulators have had vulnerabilities there — in title and status reporting especially. Keep it up to date, and leave features that answer queries with text the terminal types back for you switched off.

What Solitary prints on its own — a cell's published file names, a cloned definition's description, the messages `up` writes about it — shows control characters as `\uXXXX` rather than passing them on. Only the session you attach to is passed through, so attach only to cells running images you trust.

## Secrets exist inside the cell

The host `.env` file is not copied into the VM, but selected values become container environment variables. Container metadata can record those values until the cell is destroyed. Never treat a passed secret as invisible to the agent.

## Isolation costs resources

A VM uses memory, disk, and boot time. A cell is deliberately less convenient than a mounted container. That cost buys a stronger default boundary and a clean lifecycle.

## Allow lists need maintenance

A restricted build can fail because a package registry, image registry, DNS resolver, or CDN was omitted. This is an explicit trade-off: the policy is useful precisely because it does not silently expand.

## Early releases

The project is on its `0.x` line. Interfaces, configuration shape, and platform support can still change between releases, and each release says what moved. Do not rely on it for production security decisions yet.
