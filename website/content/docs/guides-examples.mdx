title: Example cells
description: Two complete cells to clone — a terminal setup around claude, and an editor in the browser.
---

The repository holds two cell definitions that are meant to be run rather than read. Each is a `cell.yaml`, the `Containerfile` it builds from, and a `skel/` directory of dotfiles.

- **`claude`** — a terminal working environment: claude, Neovim with LazyVim, tmux with each window marked by what claude in it is doing, `gh`, and node from nvm with corepack enabled.
- **`vscode`** — an editor reached from the host's browser: [code-server](https://github.com/coder/code-server) with the extensions a web project wants, a dark theme, and the ports a dev server listens on, plus claude, `gh`, node and corepack.

## Take one

```sh
solitary doctor
solitary clone balakin/solitary/examples/claude
solitary up claude
solitary shell claude
```

`doctor` comes first because both examples ask for `6GiB`, and its `memory` check is the one that says whether every cell you have defined fits at once — see [`doctor` checks the host](/docs/commands#doctor-checks-the-host). If it warns, lower `vm.memory` in the cloned `cell.yaml`; it is a machine setting, so it takes effect at the cell's next boot rather than immediately.

`clone` shows you what the definition asks for before installing anything, and what lands is a copy with no link back here. `--as <name>` takes one under a name of your own, which is how you keep a second copy of the same example — one to change, one to fall back to:

```sh
solitary clone balakin/solitary/examples/claude --as review
```

The first `up` builds the image inside the cell's own machine, so nothing in either `Containerfile` runs on the host. It is a slow first build — the `claude` cell installs Neovim's plugins and its treesitter parsers during it, which is what makes opening `nvim` in a fresh cell instant afterwards.

## What is in `claude`

`solitary shell claude` opens a shell in the container with everything already there:

```text
claude       the agent, from npm
nvim         LazyVim, plugins and treesitter parsers preinstalled
tmux         Catppuccin theme, status line at the top, mouse on, | and - to split
node, pnpm   node from nvm, pnpm through corepack
gh           the GitHub CLI, authenticated from GITHUB_TOKEN
lazygit, rg, fd, jq
```

Both cells declare one secret, `GITHUB_TOKEN`, and it is optional:

```yaml
secrets:
  GITHUB_TOKEN:
    required: false
    description: gh — cloning, pushing branches and opening pull requests
```

`up` offers it and enter skips it, so a cell with no token starts with the variable simply absent. It provides authentication without a browser launch from inside the cell; alternatively, open a displayed device sign-in URL yourself. Give it a fine-grained token scoped to the repositories that cell works on, and `solitary secrets claude` rotates it later. See [pass secrets safely](/docs/guides-secrets).

Sign claude in once inside the cell. The cell's home is a directory on the machine rather than in the container, so the login survives every change that replaces the container — a new image, an edited `Containerfile`, a rotated secret. It does not survive `solitary rm`, which discards the machine's disk and the home with it. Declaring `ANTHROPIC_API_KEY` under `secrets:` is the other way round: the value is held on the host, so it outlives the cell entirely. See [changing a cell](/docs/concepts#changing-a-cell).

claude does not update itself in either cell: both images set `DISABLE_AUTOUPDATER`, and silence the update notices of `gh` and `npm`. The container is started over from the image at every boot, so an update downloaded inside it would be downloaded again after every restart. Run `solitary up --rebuild claude` — or press `b` in the dashboard — to build the image again with the latest claude in it. What the `Containerfile` pins stays pinned until you change it. See [updating the tools in a cell](/docs/concepts#updating-the-tools-in-a-cell).

Each tmux window's tab shows what claude in it is doing: 🤖 while it works, 💬 when it is waiting for you — a permission to grant, a question to answer — and ✅ when it has finished. Run one claude per window and the tabs say which one needs you without visiting each. 💬 and ✅ clear as soon as you look at the window, and one never appears on the window you are already looking at; 🤖 stays until claude moves on, and the mark goes when claude exits. It is claude's own hooks in the seeded `~/.claude/settings.json` that do it, calling `agent-status`, a short script in the image that sets a tmux window option `/etc/tmux.conf` shows. A home seeded before the marks existed keeps the settings it had, so copy the `hooks` block from the example's `settings.json` into yours to get them.

The seeded `~/.claude/settings.json` sets `skipDangerousModePermissionPrompt`, so claude does not ask you to confirm that you meant to skip permissions. Make that choice deliberately: the VM separates host files and the host kernel, but these examples leave networking open and can reach host services. Delete the line if you would rather be asked, and configure `network.allow` to limit egress.

The statusline shows how much of each rate-limit window is left as a duration rather than as a wall-clock time:

```text
[Opus 5] medium | ctx:34% | 5h:12% (2h5m) | 7d:41% (3d4h)
```

A cell has no reason to agree with the host on a timezone, and `2h5m` means the same thing in both.

## What is in `vscode`

```sh
solitary clone balakin/solitary/examples/vscode
solitary up vscode
```

Then open the editor and sign in: `http://localhost:9797` opens on a login page. The port is 9797 rather than code-server's own 8080 because 8080 belongs to whatever dev server you are there to work on; it is written twice in `cell.yaml`, in `--bind-addr` and in `ports:`, and the two move together.

The editor asks for a random password, kept in the cell's home. Print the address and the password:

```sh
solitary exec vscode editor-url
```

The password is generated once per cell, the first time it starts, and kept in the cell's home like the claude login: it survives a stop and start, a new image, `up --rebuild` and a rotated secret, and only `solitary rm` (which discards the home) or deleting `~/.config/code-server/config.yaml` yourself makes a new one. `editor-url` is a script in the image that reads the port and the config file from the running server's own arguments, so the port stays written in the two places above and no third. Forwarding to **host localhost** limits network exposure, but other local users and processes can connect; keep authentication enabled. See [ports](/docs/configuration#ports).

That same forward is the thing to remember when you start a dev server inside the editor. Naming any port at all turns off forwarding every port the cell listens on, so the cell names the three a web project reaches for first alongside the editor's:

```yaml
ports:
  - 9797 # the editor
  - 3000 # next, remix, rails
  - 5173 # vite
  - 8080 # everything else
```

Anything listening on another port needs it added here, and `ports` is read when the machine boots — `solitary down vscode && solitary up vscode` is what applies a change to it.

### The editor comes configured

Eight extensions are installed at build time, from Open VSX: Claude Code, ESLint, Prettier, Tailwind CSS, EditorConfig, [oxc](https://oxc.rs) and Astro, plus GitHub's themes. Claude Code's extension is there as well as the CLI — it drives the same agent from inside the editor, against the cell's own installation.

The editor's settings — a dark theme, format on save, Prettier formatting while ESLint only fixes, and telemetry off — are an ordinary `settings.json`, seeded into the cell's home with the rest of the dotfiles:

```jsonc title="examples/vscode/skel/.local/share/code-server/User/settings.json"
{
  "workbench.colorTheme": "GitHub Dark Default",
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit",
  },
  "eslint.format.enable": false,
  "editor.tabSize": 2,
  "files.trimTrailingWhitespace": true,
  "files.insertFinalNewline": true,
  "terminal.integrated.defaultProfile.linux": "bash",
  "workbench.startupEditor": "none",
  "telemetry.telemetryLevel": "off",
}
```

code-server keeps settings on the server, in the cell, not in the browser. So they are the cell's: the same in every browser you open it from, changed from inside the editor like anywhere else, and kept from then on — a rebuilt image never touches a settings file that is already there, and `solitary rm` discards it with the home.

Workspace trust is turned off, with `--disable-workspace-trust`. Left on, the editor opens the home in Restricted Mode and disables every extension in it, the theme included, to keep code in an unfamiliar folder from running on your machine. In a cell, nothing runs on your machine, and the agent beside the editor runs code in the cell all day; the cell is the boundary workspace trust stands in for.

Extensions live on the server too. They are seeded into the home the first time the container starts rather than left in the image, so an extension you install from inside the editor stays installed and a rebuilt image does not remove it.

They need one thing more, which `seed-extensions` does at every start: the editor reads `extensions.json` and ignores any directory not named in it, so a home seeded before the image gained an extension would hold the directory and never show the extension. The two lists are merged, and the home's entry wins wherever both name one, so a version you installed yourself is left alone. An extension the image ships comes back if you uninstall it — take it out of the `Containerfile` instead.

### Nothing in it is pinned

Every build takes the newest of everything: the newest Ubuntu LTS, Node's newest LTS line, the latest nvm, `gh` from GitHub's own signed apt repository, the latest code-server, Claude Code and the extensions. So `solitary up --rebuild vscode` — `b` in the dashboard — is how this cell is brought up to date, and there is nothing in its `Containerfile` to edit for it. The one thing written down is the fingerprint of GitHub CLI's signing key; a keyring without it fails the build rather than being trusted because it arrived over HTTPS.

Each step runs the tool it installed before the build moves on, so an upstream release that breaks one fails the rebuild — and the image you already have keeps running until the next one succeeds.

## How the dotfiles get there

A cell's home is mounted over the container's, so anything an image writes under `$HOME` is hidden the moment the container runs — and the home starts empty. Both examples handle that the same way: the image ships its dotfiles under `/opt/cell-skel`, and `cell-init` copies in whatever is missing when the container starts.

```yaml
command: cell-init && exec sleep infinity
```

It never overwrites. Your edits survive a rebuild, and a file added to the skel later still arrives — but a file that _changed_ in the skel does not, because the home already has one. That is the trade, and it is the right way round for a dotfile: to take a new version of one, copy it in from `/opt/cell-skel/` yourself. Anything that has to reconcile rather than copy — the editor's extension list, above — needs a step of its own, and anything the cell does not own at all, like the web editor's settings, cannot be seeded from here.

## Restrict what it reaches

Neither example sets `network.allow`, so both reach whatever the host reaches. This is a connectivity default, not a host-network isolation guarantee: the allow list gates the **build** as well as the running cell, and a domain missing from it fails the build rather than one request.

Add it once the cell works. For `claude`:

```yaml
network:
  allow:
    # while it builds
    - archive.ubuntu.com
    - security.ubuntu.com
    - github.com
    - githubusercontent.com
    - nodejs.org
    - registry.npmjs.org
    # while it runs
    - api.anthropic.com
    - statsig.anthropic.com
    - sentry.io
```

For `vscode`, the same list plus `cli.github.com`, where `gh` is installed from, and `open-vsx.org` — needed at build time for the extensions, and again at run time if you install one from inside the editor. Either way, add whatever the code you work on has to reach.

A domain covers its subdomains, and setting `allow` at all makes the cell default-deny. [Network policy](/docs/guides-network-policy) covers what the cell sees when a request is refused.

## Make it yours

A cloned cell is a copy. Edit its `cell.yaml` or its `Containerfile` under `~/.config/solitary/cells/<name>/` and run `up` again — the image rebuilds when the build context changed, and the cell's home is kept.

The versions `claude` pins live in the `ARG` lines at the top of its `Containerfile`, which is the one place to change to move Neovim or node. `vscode` pins nothing: a rebuild moves all of it.

To take an updated definition from here without losing your `.env` or anything else you added:

```sh
solitary clone balakin/solitary/examples/claude --force
```

See [sharing cells](/docs/sharing) for what `clone` refuses to copy, and [use an image or build a container](/docs/guides-images) for swapping the toolset out entirely.
