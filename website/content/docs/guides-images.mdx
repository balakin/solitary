title: Use an image or build a container
description: Choose the toolset that runs inside a cell.
---

A cell uses either a published container image or a local `Containerfile`. The VM is the boundary; the container is replaceable tooling.

## Use a published image

Reference an image in the cell definition:

```yaml
image: ghcr.io/you/agent:latest
command: sleep infinity
```

The command is optional, but if provided it must stay running. When the image changes, running `solitary up` replaces the container while keeping the VM disk and cell home.

## Build a local image

Use `build` instead of `image`:

```yaml
build: ./Containerfile
```

The path is relative to the cell definition directory, which becomes the build context. The context is copied into the VM and the build runs there, never on the host. `.git` and `node_modules` are excluded, and the temporary context is removed after the build.

Do not set both `image` and `build`; choose one source.

## Rebuild workflow

`solitary up` reuses the existing image when the build context has not changed. Edit the `Containerfile` or its context and run `solitary up` again to rebuild. Replace the container when you want a new toolset without throwing away the cell's persistent home.

A context that has not changed can still describe a newer toolset: an unpinned package, a `latest` tag, a base image that moved. `solitary up --rebuild` builds it again without the cache that remembers what those resolved to last time, and replaces the container. That is how tools are updated, rather than by letting them update themselves inside the container, which is started over from the image at every boot. See [updating the tools in a cell](/docs/concepts#updating-the-tools-in-a-cell).

## The user inside a cell

Everything in a cell runs as root by default, and that is the right default. The machine is the boundary: the container is rootless, so its root is an unprivileged user in the machine, unable to touch the firewall, the resolver or the machine's own configuration. Root inside buys the cell nothing it should not have, and it means a global `npm install -g`, an `apt-get install` or a write to `/usr/local` inside a cell just works.

So do not add a user out of habit. Add one when something in the cell will not run as root — `limactl` refuses to, and so does Homebrew — or when the image serves a login of its own, an `sshd` for VS Code Remote-SSH or an editor server, and someone arrives in the cell as that user rather than through `solitary shell`. Then two things have to be true, one on each side.

The definition names the user, so `up` gives them the cell's home:

```yaml
build: ./Containerfile
user: cell
```

The home is a directory in the machine mounted over `/home/cell`, so it belongs to the machine's user, and a rootless container maps that user onto its own root. Naming the user mounts the home through a view instead, in which what the machine's user owns appears as theirs. Without it the home is root's, `~/.ssh` is unwritable, and everything that user does in the cell fails on a permission.

The image gives them the toolset. A user who cannot write the directories the tools live in cannot install anything, and the fix is not a workaround — it is what the boundary being elsewhere means:

```dockerfile
RUN useradd --create-home --shell /bin/bash cell \
 && echo 'cell ALL=(ALL) NOPASSWD:ALL' > /etc/sudoers.d/cell \
 && chmod 0440 /etc/sudoers.d/cell \
 && chown -R cell:cell "$NVM_DIR"
```

`sudo` for the system — installing packages, writing `/usr/local` — and ownership of anything the user installs into daily, a node prefix above all: `npm install -g` writes to the directory node lives in, and a root-owned one is where the permission errors come from. Without `sudo` the user has no way to root at all: `solitary shell` and `solitary exec` always arrive as them.

The user's id does not matter, and `up` reads it from the image rather than asking you for it: `useradd` picking the next free one is fine. Ubuntu's base image already has a user of its own at 1000, so yours usually comes out as 1001. The one limit is that a rootless container has 65536 ids to give out, so the id has to be between 1 and 65536.

What the container's command runs as does not change: the image's own user, which is the root an `sshd` needs. Only the login user gets the home, and `solitary shell` and `solitary exec` land on them too, so a file left behind by a session belongs to whoever works in the cell.

### How the home reaches the user

Each side of the mount sees the home as its own. Inside the cell it belongs to the user; on the machine it is still the machine's user's, so `solitary send` and `solitary fetch` read and write it exactly as they do in a cell that runs as root. Nothing in the home is ever re-owned, and a user whose id changes in a later image keeps the same files.

Root inside the cell can still write the home — a file it leaves there is root's in the cell, as it would be anywhere. Keep what you mean to fetch the user's, though: `solitary fetch` works from the machine's side, and a file only root can read is one it cannot read either.

The image itself runs exactly as it was built, so a cell with a user starts as quickly as one without.

### A user needs a current machine

The view is an idmapped mount, made by the machine's root before the container starts, and the machine's `mount` has to understand the `X-mount.idmap` option to make it. The default `vm.base` does, and so does any recent distribution. A machine made from an older template cannot give a user its home, and `up` refuses to start a cell with a user there rather than start it with a home the user cannot write.

A machine keeps the distribution it was created with, whatever Lima or solitary later ship. Moving a cell to a newer one means `solitary rm` and `solitary up`, and `rm` discards the home, so [fetch](/docs/artifacts) or push anything you want to keep first. A cell that runs as root has no such requirement.

## Trust the source

VM isolation prevents build instructions from executing directly on the host, but the resulting image still runs with the secrets and network permissions you grant. Review images, base images, and build definitions before using them.
