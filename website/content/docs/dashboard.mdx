title: The dashboard
description: Every cell and its state in one live view.
---

`solitary dashboard` is the same operations as the CLI in one live view: every cell, its state as it changes, and the actions that apply to the selected one.

```text
 solitary
 ╭─────────────────────╮╭──────────────────────────────────╮
 │ cells               ││ claude                           │
 │ › ● claude  running ││ image   build:./Containerfile    │
 │   ○ demo    stopped ││ machine 4 cpus · 4GiB · 40GiB    │
 ╰─────────────────────╯│ system  Ubuntu 26.04.1 LTS       │
                        │         12 updates pending       │
                        │ ports   all reach host localhost │
                        │ network 2 allowed                │
                        │         github.com               │
                        │         api.anthropic.com        │
                        │ vpn     none                     │
                        │ inbox   0 files · 0 B            │
                        │ outbox  2 files · 4.1 MiB        │
                        │ secrets 2 of 2 set               │
                        ╰──────────────────────────────────╯
 ⏎ shell · u up · b rebuild · p patch · s stop · e secrets · n network · i inspect · t traffic · d rm
```

It does nothing the commands cannot, and the slow ones it runs _as_ those commands: pressing `u` runs `solitary up --detach`, so a build prints what a build prints and a cell missing a secret asks for it the way it always does. The dashboard steps out of the way and comes back rather than owning a second, worse version of each.

## Keys

| Key               | Action                                    |
| ----------------- | ----------------------------------------- |
| `↑` `↓` / `k` `j` | Move between cells                        |
| `⏎`               | Shell into the selected cell              |
| `u`               | Bring it up (`solitary up --detach`)      |
| `b`               | Rebuild it, after a confirmation          |
| `p`               | Patch its machine (`solitary patch`)      |
| `s`               | Stop it                                   |
| `d`               | Destroy its machine, after a confirmation |
| `e`               | Manage its secrets                        |
| `n`               | Show the whole allow list                 |
| `i`               | Show what `inspect` reports about it      |
| `t`               | Follow its network traffic                |
| `r`               | Refresh                                   |
| `q`               | Quit                                      |

The list appears as soon as Lima says which machines are up. A running machine is then asked what its container is doing, each on its own, and shows `loading` until it answers — a machine that is [busy or unreachable](/docs/troubleshooting) can take the better part of a minute to, and the rest of the list does not wait on it. A loading cell can be looked at, its allow list included, but not acted on: what `u`, `s` or `⏎` would do depends on the answer. After that, every refresh shows what the machine last said while it is asked again.

## Warnings

A cell that needs something done has a `!` after its status in the list, so it is seen without being selected, and its detail view opens with a `warning` row for each thing, followed by what to do about it. `solitary ls` prints the same under its table. Each one is something that will not right itself:

- **The machine's definition was edited outside solitary**, with `limactl edit` or by hand. `u` on a stopped cell puts back what the cell describes; a running one needs `s` first.
- **A running machine holds settings that changed since it started.** `s` then `u` applies them. A stopped machine is not marked for this: `u` applies them on the way up without being asked.
- **`vm.provision` changed since the machine was provisioned.** It is the one setting stopping and starting the cell does not apply: the old script has already run, and only `d` then `u` — destroying the machine and its disk — gets one built by the current script alone.
- **The machine is missing security fixes**: updates that fix security problems are pending, or a running machine waits on a reboot to use the ones it installed. `unattended-upgrades` gets to the updates in time while the machine runs, but never to the reboot, and a stopped machine gets to neither; `p` installs them now, and asks before it restarts anything. A stopped machine shows what it was missing when it last ran.
- **`vm.base` is still set.** solitary chooses the system a machine is created from, so the line does nothing; removing it is the fix.

All of it is worked out from files on this host — the definition, the record of what the machine was given, the definition Lima keeps for it, and what the machine said when it was last asked — so the list can afford it for every cell at every refresh without asking any machine.

## The system rows

The machine's row ends with the image template it was created from — beside the container image above it, the other half of what a cell runs on — and, for a machine created from an older one, the template a new machine would get. Under it, the detail view says what the machine runs — its release and kernel — and, on the line under it, how far behind its own packages are: how many updates are pending, how many of them fix security problems, and whether an installed kernel or library waits on a reboot. The last two are in the warning colour, since they are fixes the machine could have and does not; `p` installs them.

It is the same reading [`inspect`](/docs/commands#inspect-reports-what-a-cell-runs-on) makes, and `i` shows the rest of that report in place of the detail view: the host's Lima, QEMU and kernel, the base the machine was created from, when its package lists were refreshed, its disk, the versions of the packages its isolation is made of, and the container's image and system. Any key goes back. A running cell is asked when it is selected, which takes about a second, and not again at every refresh: the answer only moves when packages do. A stopped cell shows what it said the last time it ran, and how long ago that was; one that has never been asked while running says so.

## The inbox and outbox rows

What is waiting to go in and what is waiting to come out, for the selected cell — the same two directories [`send` and `fetch`](/docs/artifacts) work on, counted rather than listed:

```text
 inbox   0 files · 0 B
 outbox  2 files · 4.1 MiB
```

They are read out of the machine, so they say `machine not running` for a cell that is not up, and `asking the machine…` for the moment between selecting a running cell and the answer arriving. An outbox with something in it is the cue to run `solitary fetch`; the dashboard does not move files itself, because where they land is the host's business and the cell's names are not to be trusted with it.

## The VPN row

Every cell has one, so a cell with no tunnel is as plain to read as a cell with one. It is refreshed while the view is open:

| Shown                                  | Means                                                                                                              |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `vpn none`                             | No tunnel configured.                                                                                              |
| `vpn configured`                       | The cell is not running, so there is nothing to ask.                                                               |
| `vpn asking the machine…`              | Running, and the first answer has not come back yet.                                                               |
| `vpn down — this cell reaches nothing` | The tunnel is not up, and the kill switch is therefore dropping everything.                                        |
| `vpn up, no recent handshake`          | Up but silent. From inside the cell this is indistinguishable from a broken network, which is why it is said here. |
| `vpn up · handshake 12s ago`           | Working, with the peer it is actually talking to and the bytes moved in each direction.                            |

The peer address is read live rather than taken from the configuration: a provider that balances one hostname across servers moves it between handshakes.

## The traffic view

`t` follows what the selected cell's network is doing, as it happens: every name it asks about, what it resolved to, and every connection the firewall refused.

```text
 ╭─────────────────────╮╭─────────────────────────────────────────────────╮
 │ cells               ││ traffic · claude                                │
 │ › ● claude  running ││ 12:07:53 query    api.github.com ×2             │
 ╰─────────────────────╯│ 12:07:53 resolved api.github.com → 140.82.121.6 │
                        │ 12:07:53 refused  example.com                   │
                        │ 12:07:53 denied   1.1.1.1:443                   │
                        ╰─────────────────────────────────────────────────╯
 ↑↓ scroll · G live · / filter · b refused only · c clear · esc back
```

| Key                                           | Action                                            |
| --------------------------------------------- | ------------------------------------------------- |
| `↑` `↓` / `k` `j`                             | Scroll                                            |
| `pgup` `pgdown` / `ctrl+b` `ctrl+f` / `space` | Page                                              |
| `g` / `G`                                     | Oldest / back to live                             |
| `/`                                           | Filter as you type; `⏎` keeps it, `esc` clears it |
| `b`                                           | Refused connections only                          |
| `c`                                           | Clear what is shown                               |
| `esc`                                         | Back to the cell list                             |

It reads the machine's log, where both halves of the allow list record what they did — so a cell cannot see, let alone edit, what is recorded about it. Repeats fold into a count, since one lookup answers with every address a name has.

This is the fastest way to find what an allow list is missing: a `refused` line names it.

## Secrets

`e` manages the selected cell's secrets: which names are set, which are not, and a masked field to set or rotate one (`↑↓` to move, `⏎` to set a value, `esc` to go back).

A name the cell declared `required: false` is marked optional, and its description is shown under it. The count in the detail pane covers every declared name, but only a missing required one colours it: a cell running without an optional secret is doing what it was asked to.

Values are never displayed. The dashboard reads only whether each declared name has one.
